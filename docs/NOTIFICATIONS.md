# 消息中心

消息中心位于 `/notifications`。质量风险、采购涨价、低余额、采集故障、控制失败和余额续航共用事件记录、接收渠道和投递结果。通知与自动调度独立：观察模式可以报警，消息系统不会修改 Sub2API 配置。

## 接收渠道

支持飞书 / Lark 自定义机器人、企业微信群机器人和通用 JSON Webhook。每个用户最多配置 8 个渠道，每个渠道分别选择通知类型。新渠道默认停用；启用后只接收之后发生的新事件，不重放历史消息。

在“消息中心 → 添加渠道”中填写接收方式、地址和订阅类型。飞书机器人开启签名校验时，同时填写签名密钥。地址与签名密钥加密保存，API 和界面只返回是否已配置，不返回明文或密文。签名密钥留空保留原值；更换签名机器人的地址时，需要重新填写或明确清除旧签名。

“测试连接”会向选中的渠道发送一条真实测试消息，即使渠道处于停用状态；测试同样记录投递结果。生产飞书群的测试需由操作员在完成配置后发起。

飞书格式与签名算法依据[自定义机器人指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)和[飞书 Webhook 说明](https://www.feishu.cn/content/7271149634339422210)。飞书和企业微信均检查 HTTP 状态及明确的业务成功码，缺失回执、签名失败、格式错误都不记为送达。消息正文作为文本处理，不允许上游名称变成机器人 @all 指令；投递不跟随 HTTP 重定向。

## 统一规则

| 事件 | 产生规则 |
| --- | --- |
| 上游质量 | 使用账号现有质量策略，包括足量错误样本、持续慢请求和恢复确认；相同状态不重复产生事件 |
| 采购价格 | 默认累计上涨 5% 起通知，同一账号冷却 60 分钟；以最近已通知倍率或后续低点为基准，小幅变化可累计 |
| 低余额 | 默认关闭；开启后默认阈值 10，按各上游返回的单位判断，同一账号持续低余额每 6 小时提醒一次 |
| 采集 / 控制 | 沿用来源隔离的事件周期，失败与恢复各自记录，单次采集重试不会重复开事件 |
| 余额续航 | 使用供应商目录已有续航阈值；样本不足或预测未知不能确认恢复 |

涨价阈值、涨价冷却、全局余额开关、余额阈值和提醒间隔统一在消息中心编辑。冷却期内被抑制的涨价不会直接丢失：采集持续成功、价格仍高于基准时，冷却结束后的下一次采价可以发出合并后的涨价信息。降价记录仍在价格历史中，但不生成普通涨价通知。

低余额检查同时核对来源代次、余额缓存身份、单位、状态和五分钟内的采集时间。旧来源或过期高余额不能触发恢复；来源或单位变化与恢复分开记录。余额数值未知时保留既有风险，不用零或成功状态代替未知。

## 事件和投递是两回事

事件发生时先写入本地记录，再为当时已启用、订阅匹配的渠道创建投递任务。这两步在同一数据库事务中完成。没有接收渠道的事件仍可查看，状态为“仅记录”。

每个渠道拥有独立的尝试次数、租约和回执。失败最多尝试五次，并逐步延长重试间隔；一个渠道失败不会重发其他渠道已经送达的消息。记录包含生成时的账号、站点、受影响分组、来源代次，以及涨价前后值等可用信息。投递记录保留生成时的渠道名称和类型，后续改名不会改写历史。

超过一小时的事件停止自动投递，以免网络恢复后集中发送过期告警。失败消息可在一小时内手动重试，但渠道必须仍启用、配置未改变，账号来源也必须仍然有效。新来源不接收旧来源尚未发送的告警。

修改渠道会取消其旧的未完成投递；正在发送时会提示稍后保存。HTTP 接收成功与本地回执落库之间仍可能发生中断，因此外部投递属于 **at-least-once**，不承诺严格只发送一次。通用接收端应按 `event_id` 去重。

## API 与兼容

| 方法 | 地址 | 用途 |
| --- | --- | --- |
| GET | `/api/v1/notifications` | 规则、渠道和最近 100 条事件及逐渠道投递结果 |
| PUT | `/api/v1/notifications/rules` | 修改通知规则 |
| POST | `/api/v1/notifications/channels` | 添加渠道 |
| PUT | `/api/v1/notifications/channels/{id}` | 修改渠道，必须带当前 `revision` |
| POST | `/api/v1/notifications/channels/{id}/test` | 发送有记录的测试消息 |
| POST | `/api/v1/notifications/deliveries/{id}/retry` | 重试符合条件的失败投递 |

新通用 Webhook 的 JSON 包含 `event_id`、`kind`、`category`、`severity`、`message`、`created_at` 和经过筛选的 `context`。迁移来的自动识别通用渠道继续使用原来的 `event_id`、`kind`、`message` 三字段格式；主动将接收方式改为“通用 Webhook”后才使用扩展格式。

迁移 033 会将原质量通知与原余额通知分别转为渠道，保留启用状态、订阅范围与密文解密用途。旧待投递质量事件保留到对应旧渠道，已送达事件不重新发送；旧余额规则和原有冷却时间也保留。旧配置表以 `_legacy` 后缀保留备查，应用不再使用它们。

旧页面 `/alerts`、`/quality-alerts` 跳转到消息中心。旧质量通知和余额设置 API 返回 `410 MESSAGE_CENTER_MOVED`，避免缓存旧页面默默写入已停用的配置表。

## 验证边界

正式回归使用本机 HTTP 模拟接收端和隔离 PostgreSQL schema，覆盖签名向量、业务错误回执、重定向、并发领取、独立重试、迟到回执、配置版本、来源变化、迁移保留、涨价累计和余额恢复。这不等于已经向真实飞书群投递成功。
