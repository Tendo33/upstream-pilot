# Sub2API 辅助能力初始审查与改进路线（历史基线）

> 本文保留改进开始前的问题与路线，不代表当前实现状态。当前结果请看 [整仓审查](REVIEW.md) 与 [验收记录](IMPLEMENTATION_LEDGER.md)。A1–C3 的代码已落地，本地验收与生产接管仍分开记录。

审查基线：Upstream Pilot `5165144`，2026-09-04。定位是辅助 Sub2API 维护分组服务质量。以下区分已复现的问题、接口契约差距和待建设能力；不把建议描述为已经实现。

## 结论与分工

当前基础覆盖采集、风险、候选排序和受控写回，但“账号看起来健康”距离“用户通过这个分组能稳定获得服务”仍有差距。作为无人值守辅助控制台，成熟度暂评 **62/100**，首要工作是修正证据和备用资格，再建立真实服务效果闭环。

建议分工：Sub2API 负责逐请求路由、并发槽位、重试、会话绑定和计费；Pilot 负责供应商质量与成本、分组服务目标、分钟级策略、风险解释和动作效果验证。Pilot 不可用时，Sub2API 应能按最后配置继续提供服务。

官方调度实现综合多种运行信号并处理会话绑定，优先级只是其中一项。因此参数读回成功还不足以证明真实请求已经转向理想上游。[Sub2API 调度实现](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/openai_account_scheduler.go)

## 初始审查确认的问题

### R1 · P1：当前来源与历史证据没有完整隔离

上一轮已经复现，本轮代码仍然存在。余额消费者只核对账号 ID、状态、时间，未校验来源缓存标识。换地址、密钥或来源后，旧零余额能影响新来源。[当前消费者](../internal/app/quality_storage.go#L75)

先比较当前来源身份与余额快照身份，失配时降为 unknown；再补来源代次到价格、探测和在途采集。来源代次应只随实际来源/凭据/映射变化，不能直接使用每次库存同步都会增加的配置计数。历史记录保留供追溯，调度只使用匹配当前来源的证据。

### R2 · P1：Sub2API 冷却中的账号仍被 Pilot 算作健康备用

Pilot 的账户 DTO 没有接收临时冷却、限流恢复和过载截止字段。备用复核读取的只是 active 和 schedulable，再结合自身样本。[DTO](../internal/upstream/sub2api.go#L49)、[备用复核](../internal/app/engine_controls.go#L284)

隔离复现：备用返回 `status=active`、`schedulable=true`，同时 `temp_unschedulable_until` 在一小时后；Pilot 仍通过备用保护并暂停主账号。

Sub2API 自身还会判断冷却、限流、过载、过期和额度等条件。[原生资格判断](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/account.go)

改进：将“手动调度开关”“近期探测健康”“原生有效候选”分开。按站点版本读取运行态约束；缺少资格证据时不得把它认证为停调保护所依赖的备用。模型、协议和组成员资格也需要纳入。

### R3 · P2：上游账号认证失败被真实请求采集器过滤

过滤器排除大部分非 5xx，只有 phase=upstream 和 429 例外，漏掉 account_auth。[过滤条件](../internal/upstream/traffic.go#L84)

隔离复现：五条成功、五条 account_auth/401，结果变成五条成功、零失败，策略给出 healthy。原生错误分类把 account_auth 归到上游错误。[Sub2API 错误分类](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/ops_user_error.go)

改进：按状态码、阶段、原因联合分类，区分客户认证/参数错误、上游认证、额度、限流、网络与模型配置问题。不能把所有 4xx 都算供应商故障，也不能丢掉明确的供应商认证错误。

### R4 · P2：控制失败与供应商健康混在一起，告警不完整

通知由质量事件键变化触发；单纯写回错误虽会保存决策，但不一定创建通知。质量列表重新 Evaluate 后，又可能覆盖持久化失败原因。[通知条件](../internal/app/engine_prices.go#L101)、[列表覆盖](../internal/app/quality_api.go#L116)

隔离复现：健康账号的优先级写回被拒绝，历史有错误记录，但通知为零，列表原因仍是“质量正常”。页面保留了 pending 标志，因此不是毫无线索，但没有明确呈现控制失败。

改进：分别展示供应商健康、采集健康和控制状态。写回失败、待确认过久、采集权限失效应建立独立事件，恢复时关闭事件；同一事件重试不重复轰炸通知。保留原有事务 outbox。

### R5 · P2：健康候选之间缺少排序防抖

排序只比较分数，缺少最小改善幅度和保持时间；现有 cooldown 主要服务风险恢复。[排序比较](../internal/quality/planner.go#L118)

纯规划复现：两候选为 100/101ms 时目标为 20/30，变成 101/100ms 后目标立即变为 30/20。这个测试证明目标会反转，不能据此声称已发生生产流量抖动。

改进：采用绝对与相对改善阈值、最短保持时间、每轮最大调整数量和恢复观察窗口。硬故障及时处理，轻微质量与价格波动使用稳定策略。阈值依据模型和服务目标校准，不设统一“神奇数值”。

## 对接契约与当前能力差距

本轮查看的官方 `/ops/requests` 明细 DTO 没有首字时间和流结束字段；Pilot 消费端将这些字段视为可选。当前回退到探测/unknown 是必要行为，但应在站点能力页明确说明。[接口数据结构](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/ops_request_details.go)

对接不能仅确认 URL 返回 200。需要版本/能力表：可用接口、可读字段、错误阶段含义、首字指标定义、读权限、写权限验证情况。优先使用该版本已有的 usage/ops 数据；缺失时用受预算限制的合成请求补测，仍无法得到的数据保持 unknown。不能用总耗时冒充首字，也不能用一次成功推断所有模型与协议。

统计口径还需区分供应商请求尝试与用户最终结果。同一用户请求可能重试多个账号；组内最终可用率应按 request_id、group_id 和最终结果归并，不能直接把成功/错误日志行数当成用户 SLA。

## 最值得建设的六项能力

| 能力 | 现在的差距 | 对使用者的价值 |
| --- | --- | --- |
| 分组服务目标与效果验证 | 主要看账号样本和写回值 | 知道可用率、首字、完整结束与成本是否达到目标，调整是否有效 |
| 版本能力与多模型/协议档案 | 一个账号一个探测模型，接口字段被动降级 | 明确 Responses、Chat、Messages、stream、tools 等能力哪些经过验证 |
| 供应商与失效域目录 | 账号数不等于独立供应商数 | 识别同平台、同余额池、同凭据或同代理的共同故障，评估备用容量 |
| 统一成本与余额续航 | 当前主要比较采购倍率 | 在相同单位和计价基准下比较真实成本，提前发现余额即将耗尽 |
| 稳定灰度与动作验证 | 参数回读之后缺少服务效果记录 | 先观察、小范围应用、检查效果，再扩大；保留人工覆盖和安全还原 |
| 事件中心与自身健康 | 账号级通知分散，后台任务状态不集中 | 直接看到受影响分组、原因、已做动作、结果、待办和采集盲区 |

### 分组目标

每个服务组配置适用模型/协议、目标成功率、首字阈值、完整结束要求、成本边界及最少独立备用。具体数值由业务设定。首页围绕“哪些组受到影响、还有哪些有效备用、最近动作是否改善结果”组织。

最小的端到端探测使用专用组 Key 和合成请求，经过用户实际的入口、限流、映射与路由。先覆盖基础文本和流式，再扩展工具调用等能力；工具探测只验证结构，不执行现实业务动作。探测会消费额度，必须有请求数、token/时间与可确定成本预算。

### 供应商与容量

增加供应商、失效域与共享额度池标识，并允许人工确认。域名可以提供线索，不能自动证明供应商独立性。读取原生冷却、额度、并发、排队和模型约束后，区分可用、降级、未知和不可调度。备用计数应针对不同失效域；承载能力不足时应明确显示。

### 成本与续航

采购倍率只有在计价基准一致时才可直接比较。逐步补齐模型输入/输出/缓存价格、币种、单位和充值换算，按实际流量结构计算成本。数据不完整时标记“不可比较”，而不是把最低倍率叫作最低实际价格。

余额续航使用近期消耗速率和额度重置时间，显示范围与可信度；样本不足时不预测。触发的是提前补充备用或告警，不等于自动改变用户售价。

### 灰度、复盘与采集预算

为计划和动作保留来源代次、目标组、配置版本、前后值和观察窗口。比对调整前后的真实结果，数据不足显示“效果未验证”。还原只处理仍由 Pilot 拥有的字段，人工修改后停止覆盖。

健康且有充分真实流量时减少主动探测，异常或冷启动时短期增加验证。校验采样配置是否可行：当前真实流量最多 300 条，minimum_samples 却允许到 1000；余额默认约五分钟刷新，证据有效期可设置为 30 秒。这些组合应提示或拒绝，避免永久样本不足与周期性 unknown。

## 可执行路线

以下是计划，不是已完成的功能。所有阶段只修改本项目；如需 Sub2API 补充接口，应另行安排目标分支与验收。

| 阶段/单元 | 负责人类型 | 依赖与范围 | 验收条件 |
| --- | --- | --- | --- |
| A1 来源证据修复 | 后端、QA | 先比较现有 cache key；再设计 source_generation 迁移，覆盖 probe、price、balance、intent | 更换来源后旧数据和晚到响应不能影响新来源，旧意图不重放，历史可追溯 |
| A2 原生候选资格 | 后端、QA | 与 A1 可并行；DTO、能力识别、备用复核 | 冷却/过载/限流/过期/额度不足账号不能充当有效备用；未知能力保守处理 |
| A3 错误与控制告警 | 全栈、QA | 修 R3/R4，独立控制状态和去重事件 | account_auth 计入正确原因；写回被拒绝时页面与通知都有明确失败，恢复可追踪 |
| B1 版本与探测档案 | 后端、前端 | A 阶段通过；扩展采集契约和模型/协议档案 | 对目标 Sub2API 版本有契约样本与兼容测试，字段缺失明确说明 |
| B2 分组目标与端到端验证 | 全栈、QA | B1；专用 Key、合成请求、日志归并和预算 | 能发现账号测试成功但分组入口失败的情形；按有效用户请求统计结果，限制探测消耗 |
| B3 动作防抖与效果记录 | 后端、前端 | A 阶段；B2 提供真实效果证据 | 小幅波动不频繁改序，硬故障及时处理，动作均能追溯到计划和观察结果 |
| C1 供应商/失效域/容量 | 全栈 | A2+B1+B2 | 同一供应商的多个账号不被误认成多个独立备用，容量未知不显示足够 |
| C2 成本标准化与续航 | 后端、前端 | A1+B1；统一价格基础数据 | 倍率、单价、币种、token 单位和充值换算分清；预测有样本与可信度约束 |
| C3 采集效率与运维入口 | 后端、前端、QA | 使用 B2 数据决定节奏 | 按站点批量采集，数据可去重；测量 SQL、内存、任务积压、整轮时延和待确认年龄 |

**Release gate：A1、A2、A3 通过之前保持观察或有人值守的有限接管。** B 阶段以目标 Sub2API 测试实例的真实入口结果验收，不能只检查参数数字。C 阶段再扩展成本优化和规模能力。

租约方面需覆盖“整轮耗时超过两分钟”的情况：当前任务租约有限，而整轮没有相同的总时限。建议续租与拥有者标识、重复任务合并、按作用域限制写回；仅有 advisory lock 能串行写入，但不能证明等待任务不会耗尽 worker。此项是代码风险分析，本轮未做长时间压力复现。

## 验证边界

本轮新增四个隔离反例，分别确认认证错误过滤、控制失败告警/展示缺口、健康排序敏感性和冷却备用误计。反例的 PASS 表示成功展示当前问题，不能作为正确行为的回归测试；实现修复时应改成断言正确结果的正式测试。

基线 `5165144` 的 [GitHub CI](https://github.com/Tendo33/upstream-pilot/actions/runs/33864841296) 已通过。本轮没有修改 Go/前端实现，也没有向生产发送探测、调整配置或发布 Release。官方源码对照是接口契约参考，不能替代目标部署版本的运行验证。

## 优先级

- **🔥 紧急且重要**：先修来源身份、原生备用资格、错误分类和控制失败可见性。
- **⚡️ 高回报优化**：版本能力表、多模型/协议档案、分组目标、端到端探测和动作效果验证。
- **🌱 长期基建**：供应商失效域、容量和成本预测、采集预算、负载测试与周期性恢复演练。
